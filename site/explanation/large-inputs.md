aless parses with a general rule engine, and that sets its costs. They are worth knowing before you point it at a large file, or let it read input you did not write.

## A whole document at a time

Most of what aless does reads the whole input and parses the whole of it before it prints anything: the viewer, `--json`, `--paths`, `--find`, `--where` and `--check`. The grammars parse complete documents, so the first byte of output comes when the parse ends. That parse runs at about a megabyte a second, and holds about 40 bytes of memory for each byte of input while it runs: on one machine, a 4.4 MB JSON document loaded in about three and a half seconds and a 60 MB one in 45, at a peak of 2.1 GB. Moving around the tree afterwards is fast whatever its size, because the engine is no longer involved.

`--path` and `--depth` make an answer small, not the parse. A pipe that stops reading early, as `head` does, ends aless without an error.

## Streaming

`--render` and `--alchemy` work differently, because their output is a stream of records rather than one answer. JSON Lines, CSV and TSV are read a window at a time, so a file of any size passes through in the memory of one window. For the JSON family, jsonic, CSV, TSV, YAML, ZON, XML, PGN (a game at a time) and most annotated grammars from the command line the records are written as the parse proceeds, and for most of them the records already written are not kept; the other formats are parsed whole and then streamed. JSON, JSONC, JSON5, jsonic, JSON Lines, CSV, TSV, YAML, ZON, XML and PGN are written through the transducers their packages ship, which make the records of the parse's steps: on one machine that takes about a tenth to a fifth longer than the parse alone for JSON, JSONC, JSON5 and JSON Lines, two fifths longer for CSV and TSV, three and a half to four times as long for jsonic, ZON, YAML and XML, and six times as long for PGN. Since nothing of the parse is kept behind the records, it holds about 7 to 15 bytes for each byte of input, where a whole parse holds about 40, and a JSON or JSONC file, which is read a window at a time, holds one window whatever its size. TOML, INI, Markdown, CSS, feeds, `.proto`, expressions, versions, C and the grammar notations say why in the loss note's `whole`, each in its own words: in TOML a later header can add to a table, in INI it can name a section again, in Markdown a link can name a definition that comes later, in C a conditional group is folded into one node only once the whole file is parsed, and in a grammar notation a rule can be named before it is defined. In each, a document's tree is complete only at its end. A grammar that cannot stream a particular document, such as a YAML file holding several documents, is read whole instead, as long as nothing has been written yet. So is a JSON Lines file with a record that repeats a key, and a CSV or TSV file whose header names a column twice, which their streams would hold twice where the output cannot keep the last of the two, as `--render json` cannot; standard input cannot be read twice, so there that record fails the run.

A stream cannot take back what it wrote. When one fails part-way, what it had written stays on standard output, every record whole and none in part, and the error says `"output": "partial"`. A stream also reads ahead of what it writes, a window of 64 KB for JSON Lines, CSV and TSV, so when a writer to standard input goes quiet and `--timeout` stops the run, the records still in that read-ahead are not written.

## The limits

Three limits keep an input from taking the machine down, whether it is large, slow or written to hurt:

| Limit | Default | Refuses |
|---|---|---|
| `--max-size` | 64 MB | an input over the size, before a file is read, or as soon as standard input passes it |
| depth | about 1,000 levels, lower in most grammars | a document nested deeper, with the `too_deep` code |
| `--timeout` | none | a parse past the time, with how far it got |

The depth limit is not optional. Some grammars would recurse until the stack ran out and take the process with them, and slow down with the square of the depth before that, so most grammars stop sooner of their own accord: JSON, JSON Lines, JSON5, jsonic, YAML, TOML, INI, ZON and expressions at 127 levels (an expression at 127 operations, too), XML at 256 open elements, JSONC at 512 levels and CSS at 768 open rules, a `.proto` file is refused before it is parsed when its braces nest past 100 levels, and C stops at its reader's limits, an expression of 127 operations, 1,024 open rules or a syntax tree 256 levels deep, and a grammar in ABNF, EBNF or GBNF at its compiler's limits, groups and options nested about 500 levels in ABNF, 130 in EBNF and 128 in GBNF, and elements nested 128 levels. C's tree has one more bound, of aless's: its reader repeats a node's subtrees under the members that name them, so each level of a chain of subscripts or member accesses doubles the tree written out, and aless stops before writing out one of more than 256 values a byte of the file (a million at least, and never more than 33,554,432, however long a comment makes the file), or of more than 2,048 bytes of names and strings a byte (8 MB at least, and never more than 256 MB), so that a long name in a repeated subtree is held too. The time limit has no default, since how long a parse should take depends on the machine; a program with a deadline of its own should pass one a little shorter, and get an error it can read rather than a kill. A grammar's compiler is the one reader the limit cannot stop part way, so past it aless stops waiting for the compile and reports a `timeout` error, and starts no other compile while that one runs on, nor any once the time is up; the compile takes time that grows faster than the grammar's rules, and the compiler refuses, before building anything, a grammar whose left-recursion pass would multiply the alternatives a cycle of rules starting with one another makes, or copy past its bound the elements a long chain of rules led by one another makes.

None of the limits makes parsing a hostile input free: they bound what one can cost. Raise `--max-size` for a large file you trust, and keep it for input you do not. The [reference](/reference/command-line.html#large-inputs-and-streaming) states every limit exactly.
