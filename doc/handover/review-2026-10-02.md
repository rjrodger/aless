## 2. aless

### 2.1 State

Healthy. Every gate the repository names is green on main; CI on main has been green on Linux, macOS, Windows and the 1.88 MSRV job for the last 20 runs. The agent contract (README "Scripts and agents", `--help`, `skills/aless/SKILL.md`, the tests) agrees with the binary: every exit status 0 to 6 and every error kind came out of the binary with the documented fields, and the README's worked examples reproduce byte for byte. The viewer's key map matches the README and jless; reload re-anchoring, watch, explorer caps, colour and width handling behave as documented. No unbounded growth was found.

### 2.2 Confirmed findings

Major (each verified by a second agent):

1. **CSV and TSV positions are wrong for the first field.** `src/prov.rs` aligns record 0's first key against the header cell, so `[0]` and `[0].<first>` report line 1 and `--where --at 2:1` answers the second field. The contract calls these formats exact. Repair: skip the header record's tokens before aligning record 0; add a test on `sample.csv`.
2. **`--at` never returns exit 4 while any node has a position.** It snaps to the last positioned node before the position; a position past the end of the file answers the last node with exit 0. The contract promises exit 4 when `--at` names nothing. Document the snapping (README, `--help`, SKILL.md) or make a position past the last positioned line a `not_found` with `nearest`.
3. **The move to crates.io (issue 28) cannot ship yet.** Tried in a scratch copy: the manifest change is exactly what the plan says (19 dependency lines, 20 patch tables, one engine 0.12.8, MSRV 1.88 held by ratatui), but `cargo check` fails with 30 errors. aless main calls API that exists only on the unreleased main of twelve crates (`manifest_text`/`render_text`/`lift_text` in json, jsonc, json5, jsonic, jsonl, toml, ini, xml, zon and markdown; `TreeContract` in transduce; `Source::new`/`export_as` in alchemy), and the published transduce 0.1.0 requires csv ^0.5.11 while aless needs 0.6.0, so two `CsvOptions` types collide. Issue 28 names yaml as the only blocker; yaml 0.5.16 is published and no longer blocks. The real blocker is a release wave of those twelve crates and a transduce release.

Minor defects (all reproduced on the debug binary unless noted):

- A watched file rewritten more often than every 120 ms never reloads while the writes continue (the debounce resets per event; ticks run only when idle).
- Multi-digit counts do not accumulate in the source view (`12j` scrolls 2 lines).
- The mouse wheel scrolls an overlay past its last line into blank rows.
- `:w FILE` from a tab whose file never parsed writes `[]` and reports success.
- A failure part way through a streaming run drops up to 32 KB of complete, already-rendered records held in the renderer's buffer; on a slow stdin with `--timeout` this leaves `output: none` though a record had parsed. Issue 17's record-boundary promise otherwise holds.
- A lost-wakeup race between the alarm thread and `materialize` (Relaxed atomics) can leave the value walk with no deadline. Read from the code, not reproduced.
- A `--render` fallback on a file restarts the time limit, so a run can take up to twice `--timeout`.
- A jsonic implicit root whose first member is an object is placed at that member's brace.
- A json5 document combining Infinity, NaN, -Infinity and 1e400 loses positions after the first.
- `--render json` writes a repeated member twice (SKILL.md says once) and refuses NaN and Infinity that `--json` writes as null.
- Collapsed previews with wide characters are cut mid-item (the preview budgets in chars, the screen in cells).
- A usage message carries a 14-space run; the `[-1]` message prints 4294967295.
- `unicode-width` is declared and unused (a dependency change, so the maintainer's call).

Documentation drift: `loss` rides on usage and not_found errors under `--render` though the README says a usage error has only kind and message; the exactness sentence omits jsonic and feed; `nearest` and `keys` can be null and `keys` is capped at 20; `--check` folds every failure kind into exit 1; README "Commands" and the F1 help omit `:yank`, `:tabfirst`, `:tablast`, `:e!`, `:tabnew` and several `:set` options; a single `g` goes to the top where jless needs `gg`; Cargo.toml, README and AGENTS.md still say tabnas-lsp is not on crates.io (published 2026-09-30).

## 4. The fleet (37 repositories)

### 4.1 Overall

Every COMPONENT and TOOL with code carries all three runtimes, in version lockstep across every site, with CI green on main and the current version published on npm, the Go proxy, crates.io and a GitHub Release, except transduce, render and alchemy (4.4) and the crate gaps in 4.5. Shared fixtures run in all three runtimes everywhere except bnf and ebnf (no shared fixtures; bnf is held to a recorded TS oracle in Rust only, ebnf's Go front end is a hand-written scanner), skills (no code) and mcp (TypeScript only, by design). The verdict "complete against TypeScript" holds for the plugin surface of every grammar repository audited; the gaps below are value differences, record keeping, publication and gates.

### 4.2 Cross-cutting patterns

1. **Divergences recorded in prose, not registers.** Executable registers exist in parser, jsonic, json5, toml, feed, css, c, proto, support and jsonic-cli. The rest (json, jsonl, jsonc, yaml, ini, csv, xml, zon, markdown, abnf, bnf, ebnf, gbnf, hoover, semver, chess, expr, directive, path, multisource, debug, railroad, render, transduce, lsp) keep theirs in README or AGENTS text pinned by single-runtime tests, which ADR-14 calls a defect. Several registers (feed, c) are asserted by Rust alone; transduce handles its two as a by-name skip list that is now stale.
2. **Rust depth caps.** The Rust ports refuse nesting past a fixed depth (127 for the jsonic family, 256 for xml and feed, 512 for jsonc, 768 for css, 100 for proto) with the engine's `cancel`, where TS and Go parse. Deliberate and documented, almost never registered.
3. **Stale "unpublished" prose.** Nearly every rs/README, Cargo.toml comment, Makefile and AGENTS.md still says the crates are not on crates.io and tells consumers to clone siblings. All are published; semver's Rust install documentation is wrong for every consumer.
4. **Go modules one engine patch behind.** Every go.mod requires parser/go v0.12.7; 0.12.8 shipped on 2026-10-01 (dependencies are to track the latest release). jsonic-cli is further behind (parser 0.12.2, jsonic 0.7.1, debug 0.3.8, json 0.5.10). The committed rs/Cargo.lock files likewise record 0.12.7 (exempted by each `ci/rust/run.sh`).
5. **Translation parts are Rust-only.** `manifest_text`, `render_text` and `lift_text` exist only in the Rust crates, by design (the host is Rust); npm and Go packages ship nothing equivalent.
6. **Rust gated nowhere in two repos.** chess and lsp publish a crate at every release and have no rust.yml; the shared polyglot-ci has no cargo step, so their Rust ports are tested only by hand.
7. **Authority inverted in two repos.** transduce and alchemy (and render) name Rust the reference runtime and anchor their version tests on rs/Cargo.toml, against the fleet's TypeScript-canonical rule, with no recorded decision.

### 4.3 Real value differences and defects found (verified unless marked)

- toml (Go): a redefined key is accepted silently where TS and Rust raise `toml_key_conflict` (reproduced: `a = 1\na = 2` gives `{"a":2}`; `a = 1\n[a]\nb = 2` gives `{"a":1}`, dropping the table; nine BurntSushi invalid documents accepted). Acknowledged in AGENTS.md, not registered; toml's register has no Go column.
- yaml (Go, issue 108): `*al: a` gives `[null,"a"]` where TS and Rust give `{"*al":"a"}`.
- json5 (Go, issue 83): `unprintable` where TS and Rust say `unexpected` (verifier: minor; the string check runs after jsonic's pre-scan matcher).
- xml (Go): an `<!ENTITY>` whose name starts outside the BMP is recorded in Go and skipped with `undeclared_entity` in TS and Rust (verifier: minor).
- expr (Go, issue 64): a dangling operator yields a self-referential tree that loops `Simplify` and `json.Marshal`; (TS, issue 62) `(1?2:3)+1` evaluates to 4 in TS and 3 in Go and Rust; a ternary inside a map or list is wrong in all three, differently.
- proto (Go): four registered, unrepaired divergences in `build_descriptor.go` (`-0x10` becomes -16, `1_0` becomes 10, `__proto__` kept, proto3 options discarded). Rust: parse time quadratic in elements per repetition (400 fields 10.1 s in a debug build against 0.129 s in TS).
- gbnf (Go): a surrogate-pair escape decodes to two U+FFFD; no renderer, no `gbnf-check`, no TS oracle, live corpus compile-only.
- abnf (Go): an adjacent surrogate pair in a dotted numeric value decodes to two U+FFFD. The "Rust engine quadratic on long rules" claim was refuted: the engine fix landed in parser 193 and 195; only debug-profile wall-clock remains (abnf issue 81).
- ebnf (Go): hand-written scanner, not the canonical rule table; not held to the TS oracle.
- ini (Go, issue 81): the shared default instance races (confirmed with the race detector) though documented as safe.
- c: a ternary as a whole declaration initializer kills the Go process (uncatchable stack overflow); the Rust corpus match is 63 of 100; two Rust-only resource defects (issues 47, 48); the tree doubles per binary operator in all three (issue 53).
- bnf: the replace-loop compiler (bnf 80) is on main but unreleased, so every npm and Go consumer still compiles repetitions as push chains (issue 93); Go `optionsToData` drops CommentDef lex, eatline and suffix (issue 63); Go has no byte-for-byte oracle against the TS emitter.
- debug: Go `Abnf()` does not render the bnf 80 repeat loop (issue 67) and the published 0.3.9 of every runtime predates the repeat-loop rendering, so the current abnf/ebnf/gbnf output is misrendered by every published debug.
- path (Rust): a child path is keyed on the parent rule name, so a host whose pair pushes a rule not named `val` gets no path.
- css (Rust): the engine-based port on main is published nowhere; crates.io 0.5.9 is the old standalone implementation under the same version, so the next release must bump.
- jsonic-cli: the Rust crate has never been published (every release.yml run fails its crates job); the canonical TS command exits 0 after a failure where both ports exit 1 (repair in TS per ADR-13, no issue open); Go installs plugins in map order.
- lsp: published 0.1.3 predates the whole Rust port (main is 46 commits ahead); the crate's rs/v0.1.3 is on a different commit from the npm and Go 0.1.3; parse budget and document-size cap are wired only in Rust; the 262-case diagnostics corpus is executed by no test; Go declares two JSON-RPC error codes where Rust declares five.
- multisource (Go): `map.merge` is invoked once per key rather than once per node; processor aliasing not expressible; nested-parse meta omits `fileName`.
- railroad: the CLI's grammar mode is a fixed table in Go and Rust where TS requires any module.
- skills: the five skills describe a two-runtime fleet, teach three version constants where releases move six, and call DIVERGENCE.md the single record although ADR-14 requires the register.
- mcp: bundled `data/error-codes.json` carries engine 0.12.2 and `data/DIVERGENCE.md` differs from parser's by 90 lines; `npm test` in the fleet layout fails its staleness gate; the tool count is documented as six where seven exist.

### 4.4 transduce, render, alchemy

The TS and Go ports landed on 2026-10-01 and are published nowhere except crates.io: no npm package, no `ts/v` or `go/v` tags, no `release.yml`, `ci.yml` or `deps-gate.yml`, and (alchemy, marked COMPONENT) no stamped clib, against what ADR-20 requires (admin issues 97 and 102). The only workflow is rust.yml, path-filtered to rs/, so neither port has ever run in CI; the Go port merges ran nothing but CodeQL. The Go modules do not build against published modules: transduce calls csv 0.6.0's `Make` while requiring 0.5.11; render and alchemy require `go/v0.1.0` tags that do not exist. transduce's incremental source is compiled only under the `tabnas_nodecell` build tag, so a default build refuses every incremental run and 30 of 113 Go tests skip; alchemy's `run` path is unverified in a default `go test`. All three go.mod files still require csv 0.5.11 and yaml 0.5.15. Their docs still say "Rust only for now". The fleet's release lists do not include them, and alchemy's COMPONENT mark is not in ADR-20's roster.

### 4.5 Publication and tags

Every release's three tags and npm's gitHead agree, with these exceptions: yaml 0.5.16, csv 0.6.0 and jsonic-cli 0.5.9 have no rs/v tag (yaml and csv crates were published by the workflow without a tag; jsonic-cli's crate has never been published); lsp's rs/v0.1.3 is on bf749e6 while ts/v and go/v are on 7e73b38, so three registries say 0.1.3 for two different trees. semver has a stray ts/v0.1.1 tag with no npm, go or rs counterpart. chess also publishes a web component (`@tabnas/chess-view`) whose release.yml comments call it `@tabnas/chess-game`.

### 4.7 What the completeness critic flagged, and what stands

The critic's valid points: the admin repositories measure, status, web and .github were not audited (measure may hold cross-runtime benchmarks); kind marks were never checked against ADR-20's roster (alchemy's COMPONENT mark is not in it); nested Go modules and the Python bindings had not been run (now run, all green); release-tag agreement had been checked for two repositories (now for all, 4.5); the "divergences" column mixes register rows with prose entries; "CI green" means "builds against sibling main" for TS and Go under the shared workflow, which is how transduce, render and alchemy are green while failing against published modules. Two of its points do not stand: TypeScript suites were executed (the fleet gate ran all 29 published TS suites, plus parser's own), and Go plugins were run against 0.12.8 (the fleet gate wires the working-tree engine); what was not run is each repository's TS suite at main, and no Rust crate was tested against a crates.io engine.
